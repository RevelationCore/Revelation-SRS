    <h1>The Revelation Student Records Enterprise Reference Model</h1>
    <p>This article presents an updated version of our Student Records Enterprise Reference Model, building on our
      earlier blog, <a href='https://revelationcore.com/blogs/a-student-records-enterprise-reference-model.html'>A
        Higher Education Enterprise Reference Model for Student Records</a>.</p>
    <p>The updated model is intended as a working reference for architects and analysts operating around the Student
      Information System (SIS). It extends the original scope beyond core SIS integrations to provide a fuller UK higher
      education view spanning operational systems, statutory bodies, student support processes, examination operations,
      and academic governance.</p>
    <p>You can explore the interactive model here: <a
        href='https://www.revelationcore.com/app/index.html?model=/app/reference/models/revelation-student-records-enterprise-reference-model-3.0.json'><strong>View
          the model in the Revelation EA tool</strong></a>.</p><img class='hero-image'
      src='https://revelationcore.com/assets/svg/revelation-student-records-enterprise-reference-model-2.1.svg'
      alt='Higher Education Student Records Enterprise Reference Model'>

  <section class="blog-article">
    <h2>What’s Changed in This Version</h2>
    <p>Version 3.0 keeps the same 33 systems and actors and 69 flows introduced in 2.1, and makes two changes: a new
      flow identifier scheme, and a direct link to the open-source implementation this model has since informed.</p>
    <ul>
      <li><strong>New flow identifier scheme:</strong> flows were previously numbered <code>F-CM-SIS-01</code>–<code>F-SIS-AI-01</code>
        in a single flat sequence with no gap tolerance (version 2.1 has no <code>F054</code>, an artefact of the flat
        numbering) and no information content — nothing about <code>F-SIS-HESA-01</code> tells you it concerns HESA. Flows are
        now identified as <code>F-&lt;FROM&gt;-&lt;TO&gt;-&lt;nn&gt;</code>, for example <code>F-SIS-HESA-01</code>: the
        source and target system codes plus a two-digit sequence local to that ordered pair. A new flow between an
        existing pair of systems simply gets the next local sequence number; a new flow between a pair that has never
        exchanged data starts its own sequence at <code>01</code>. No flow's identifier ever needs to change because a
        flow was added elsewhere in the model, and the identifier itself now tells you what the flow connects.</li>
      <li><strong>Reference implementation:</strong> this model has since informed <a
          href='https://github.com/RevelationCore/Revelation-SRS'><strong>Revelation SRS</strong></a>, an open-source
        student records system. See <a href="#reference-implementation">Reference implementation</a> below and the
        <strong>SRS status</strong> column in the systems portfolio for how each system in this model maps to the
        current open-source build.</li>
    </ul>
    <p>Everything else — the 33 systems, the 69 flows, their descriptions and typical data exchanged — is unchanged
      from version 2.1. The remainder of this section describes what changed in <em>2.1</em> relative to the original
      accelerator, for readers arriving at this article for the first time.</p>
    <p>The original accelerator described <strong>24 systems</strong> and <strong>26 core SIS flows</strong>. Version
      2.1 expanded that scope to <strong>33 systems and actors</strong> and <strong>69
        flows</strong>, turning the original integration-focused view into a broader enterprise reference for UK higher
      education architecture.</p>
    <ul>
      <li><strong>Broader scope:</strong> the model now extends beyond core SIS integrations into analytics, research,
        digital services, statutory reporting, student support, examinations, and academic governance.</li>
      <li><strong>New systems and actors:</strong> additions include Student Wellbeing &amp; Disability, Exam
        Scheduling, Academic Integrity, Exam Board, External Examiner, and UK sector bodies such as UCAS, HESA, the
        Student Loans Company, and UK Visas &amp; Immigration.</li>
      <li><strong>Expanded flow coverage:</strong> the original model covered 26 core SIS flows. The 2.1 update added
        flows for analytics and warehousing, student evaluation, HR and payroll, research administration, content and
        service management, statutory returns, wellbeing and adjustments, examinations, board ratification, external
        examining, and academic misconduct.</li>
      <li><strong>Clearer system-of-record boundaries:</strong> Student Records is now described explicitly as the
        authoritative student record and outcome system, while source systems such as Finance, Wellbeing, Research
        Proposals, and Academic Integrity retain ownership of their own business processes.</li>
      <li><strong>UK-specific architecture:</strong> statutory and regulatory obligations are now modelled directly,
        rather than assumed, including HESA returns, SLC confirmations, UKVI sponsor-compliance data, and UCAS
        admissions exchange.</li>
      <li><strong>Academic governance made explicit:</strong> the model now distinguishes between systems that process
        and present data and actors that make formal academic decisions, supported by Exam Board and External Examiner
        flows.</li>
    </ul>

  <section id="reference-implementation" class="blog-article anchor-scroll">
    <h2>Reference Implementation</h2>
    <p>This reference model has since informed <a href='https://github.com/RevelationCore/Revelation-SRS'><strong>Revelation
          SRS</strong></a>, an AGPL-licensed, open-source student records system for UK higher education. Revelation SRS
      is a separate project under a separate licence from this model (see Licence, below) — it is a working
      implementation that the model's authors have used to test the model against real build decisions, not a
      certification that the model is complete or that any given institution's landscape matches it.</p>
    <p>Building a real system surfaced places where the model's logical flows and an actual implementation diverge.
      Two are architectural choices worth calling out explicitly:</p>
    <ul>
      <li><strong>Curriculum, exam scheduling, and academic misconduct are consolidated natively in the SIS core</strong>
        rather than modelled as separate systems synced via a flow. Revelation SRS builds programme/module authoring,
        exam-entry logistics, and misconduct casework directly into the core platform. The corresponding flows
        (<code>F-CM-SIS-01</code>/<code>F-SIS-CM-01</code>, <code>F-SIS-EXAMS-01</code>/<code>F-EXAMS-SIS-01</code>,
        <code>F-AI-SIS-01</code>/<code>F-SIS-AI-01</code>) describe a valid integration pattern for institutions that
        run separate products for these capabilities, but they are not how Revelation SRS itself is built.</li>
      <li><strong>Attendance is a native pluggable module, not an external feed</strong> — matching the outcome-ownership
        pattern this model uses for Wellbeing. Revelation SRS's attendance and engagement capability
        (<code>modules/attendance</code>) owns its own casework and hands the SIS only the confirmed engagement
        outcome, exactly as Wellbeing hands the SIS an approved-adjustment outcome. The raw-attendance-feed flow this
        model assumes (<code>F-AM-SIS-01</code>) — a third-party Attendance Monitoring product pushing raw records
        into the SIS — is not implemented and is not currently planned; Revelation SRS's attendance module is a
        first-party capability of the same product, not an adapter for an external system.</li>
    </ul>
    <p>Beyond these two deviations, most systems in this model fall into one of two states in the current Revelation
      SRS build: implemented substantially as modelled (as a separate system or module exchanging the outcome data
      this model describes), or not yet built. Some of the latter are on the product roadmap (Finance, Timetabling,
      EDRMS, Business Intelligence, Data Warehouse, HR, CRIS); others — CRM, Library, Accommodation &amp; Conferencing,
      Estates, Online ID Verification, Student Evaluation of Teaching, Payroll, Research Proposals, Content Management,
      and IT Service Management — have no code and no scheduled work in Revelation SRS today. The systems portfolio
      table below records this per system as <strong>SRS status</strong>; treat it as a snapshot taken at the
      version noted at the top of this article, not a permanent commitment.</p>

  <section class="blog-article">
    <h2>Model Overview</h2>
    <p>Student Records sits at the centre of the model as the institutional system of record for the student academic
      lifecycle. Around it are domain systems that originate or consume data: teaching and learning platforms,
      operational services, analytics tooling, research systems, digital workplace services, and external statutory
      bodies.</p>
    <p>The updated model distinguishes three architectural roles:</p>
    <ul>
      <li><strong>Source and operational systems</strong>, such as the VLE, Timetabling, Finance, Attendance Monitoring,
        Wellbeing, and Exam Scheduling.</li>
      <li><strong>Core record systems</strong>, with Student Records consolidating the student’s authoritative
        institutional record and ratified academic outcomes.</li>
      <li><strong>Governance actors</strong>, such as the Exam Board and External Examiner, who review and ratify
        outcomes rather than own operational processing.</li>
    </ul>
    <div class='callout callout-uk'>
      <p><strong>UK architecture note:</strong> the model now embeds sector-specific obligations directly in the
        reference architecture. That includes UCAS admissions exchange, HESA data returns and identifiers, Student Loans
        Company confirmations, and UKVI sponsor-compliance flows. These are not optional embellishments in a UK context;
        they are core integration considerations for an SIS landscape.</p>
    </div>
    <p>For architects, the main value of the model is not simply the application inventory. It is the assignment of
      responsibility: which system originates data, which system owns the lasting institutional record, and which actors
      apply judgement or assurance before outcomes are confirmed.</p>
  </section>
  <section class="blog-article">
    <h2>Model Principles</h2>
    <p>This model has been developed around a set of governing principles that reflect common practice in UK higher education. Understanding these principles helps architects apply the model appropriately and identify where local deviation may be justified.</p>
    <h3>Student Records as system of record</h3>
    <p>The SIS is the institutional system of record for the student academic lifecycle. It holds the authoritative data about who is enrolled, what they are studying, how they are progressing, and what outcomes have been confirmed. All other systems that generate or affect student data are expected to pass the relevant outcome to Student Records.</p>
    <h3>Process ownership versus outcome ownership</h3>
    <p>Other systems manage their domain processes and pass the confirmed outcome to Student Records. Finance manages billing; the fee liability and hold status sit in the SIS. Wellbeing manages adjustment cases; the approved outcome sits in the SIS. The Exam Board ratifies results; the ratified decision is written to and locked in the SIS. This principle prevents data fragmentation and ensures a single, auditable record for each student.</p>
    <h3>SIS as distribution hub</h3>
    <p>Because the SIS holds the authoritative record, it is also responsible for distributing confirmed outcomes to downstream operational systems. Attendance Monitoring receives approved adjustment thresholds from SIS rather than directly from Wellbeing. The VLE receives adjustment delivery requirements from SIS. This pattern reduces integration complexity and prevents divergent states across systems.</p>
    <h3>Governance actors are not systems of record</h3>
    <p>The Exam Board and External Examiner are modelled as actors rather than systems. They receive data, apply judgement, and return decisions — but they do not own records. This distinction preserves the integrity of the student record and reflects the governance reality that formal academic decisions are made by people, not systems.</p>
    <h3>UK regulatory compliance as a first-class concern</h3>
    <p>Statutory and regulatory obligations are treated as core integration requirements. HESA data returns, Student Loans Company confirmations, UKVI sponsor compliance data, and UCAS admissions exchange are first-class flows in this model because in a UK HE context they carry legal and financial consequences and must be planned for from the outset of any SIS programme.</p>
    <h3>Local variation</h3>
    <p>This model represents a generalised UK higher education architecture. Individual institutions will vary from this pattern. Some operate more lateral data flows between systems, with less centralisation through the SIS. Some have fewer or more systems, or use product suites that consolidate multiple capabilities. Some have integration middleware that alters the physical routing of data. The model is a reference for mapping, gap analysis, and programme planning — not a normative prescription. Institutions should adapt it to reflect their specific systems, history, and governance practice.</p>
    <h3>Nature of information flows</h3>
    <p>Flows in this model are logical rather than technical. The physical implementation of any flow may be a real-time API integration, a scheduled batch extract, a portal-based self-service action, a manual process carried out by registry or administrative staff, or an electronic file transfer. The model does not prescribe integration technology; it establishes what data should flow between which systems and who owns each element of the student record.</p>
  </section>
  <section class="blog-article">
    <h2>Applying the Model Locally</h2>
    <p>The reference model is a starting point, not a deliverable. Its value is realised when institutions use it as a lens against their own landscape — comparing what is modelled here against what they actually have, identifying gaps, and scoping the work needed to close them.</p>
    <p>A typical application follows a progression from orientation to execution:</p>
    <h3>Domain and system identification</h3>
    <p>Begin by mapping the reference model against your institution's actual application inventory. Identify which systems in the reference model you operate, which capabilities are served by different products, and where there are genuine gaps — domains present in the reference model but not yet covered locally. This gives you a scoped, institution-specific version of the model as a baseline.</p>
    <h3>Business analysis and requirements</h3>
    <p>For each domain or integration gap identified, use the flow descriptions in this reference as a starting point for business analysis. The flow type classifications — SOR intake, SIS distribution, outcome confirmation, statutory — help orient conversations about data ownership and process boundaries. Work with domain leads to confirm what data is exchanged, who owns it, and what business rules govern it in your local context.</p>
    <h3>Functional flows</h3>
    <p>Translate the logical flows in the reference model into institution-specific functional flows. These describe what happens in your processes, using your system names, your data structures, and your business rules. Functional flows are the bridge between the reference model and your detailed design — they confirm the scope of each integration and surface dependencies before implementation begins.</p>
    <h3>Detailed as-is and to-be modelling</h3>
    <p>Where significant change is planned — a SIS replacement, an integration remediation, or a new domain capability — develop detailed as-is and to-be models for the affected scope. This may include process models, data flow diagrams, and sequence diagrams that describe the precise message exchange, trigger conditions, error handling, and data transformation for each integration. Revelation supports this progression from logical reference model through to detailed design artefacts.</p>
    <h3>Transition roadmap and work packages</h3>
    <p>Use the scoped system inventory and detailed models to build a transition roadmap. Group related integrations and domain changes into work packages that can be sequenced, resourced, and governed independently. Statutory flows such as HESA, SLC, and UKVI typically carry fixed delivery deadlines and should be identified early. Core SIS integrations — VLE, Finance, IAM — are usually foundational and will unblock other work packages downstream. The reference model's flow groupings provide a natural starting point for work package boundaries.</p>
  </section>

    <h2>Detailed Flow Reference</h2>
    <p class='small'>Each section below is intended as a practical architecture reference. The “Typical data exchanged”
      list is illustrative rather than exhaustive, but reflects the principal data classes implied by the model and its
      underlying process boundaries.</p>
  <section id="F-CM-SIS-01" class="blog-article anchor-scroll">
      <h3>F-CM-SIS-01: Curriculum Mgmt to Student Records</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Programme and module catalogue updates &nbsp;|&nbsp;
        <strong>From:</strong> Curriculum Mgmt &nbsp;|&nbsp; <strong>To:</strong> Student Records</div>
      <p><strong>Description:</strong> Curriculum Management is the official source of programmes, modules, and
        prerequisites. This flow updates the Student Records catalogue with current academic structures, ensuring
        consistent enrolment, registration, and progression records.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Programme details</li>
        <li>Module details</li>
        <li>Prerequisite and co-requisite rules</li>
        <li>Retired structures</li>
        <li>Progression structures</li>
      </ul>
      <p><strong>Flow type:</strong> SOR intake — CM is the system of record for programme and module design; SIS consumes this catalogue to govern what students can register for.</p>
      <a href="#flows">Back to Flows</a>
  </section>
  <section id="F-SIS-CM-01" class="blog-article anchor-scroll">
      <h3>F-SIS-CM-01: Student Records to Curriculum Mgmt</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Enrolment, completion, and performance metrics &nbsp;|&nbsp;
        <strong>From:</strong> Student Records &nbsp;|&nbsp; <strong>To:</strong> Curriculum Mgmt</div>
      <p><strong>Description:</strong> Student Records provides enrolment, completion, and performance metrics to
        Curriculum Management. These analytics inform data-driven updates to programmes, modules, and prerequisites.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Enrolment counts</li>
        <li>Completion and outcome data</li>
        <li>Grade distributions</li>
        <li>Retention insights</li>
        <li>Curriculum review metrics</li>
      </ul>
      <p><strong>Flow type:</strong> SIS distribution — Analytics derived from SIS are read-only inputs to curriculum review; CM should not modify or override this data independently.</p>
      <a href="#flows">Back to Flows</a>
  </section>
  <section id="F-SIS-TTB-01" class="blog-article anchor-scroll">
      <h3>F-SIS-TTB-01: Student Records to Timetabling</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Student enrolment and module registration data &nbsp;|&nbsp;
        <strong>From:</strong> Student Records &nbsp;|&nbsp; <strong>To:</strong> Timetabling</div>
      <p><strong>Description:</strong> Student Records provides key enrolment information needed by the Timetabling
        system to create accurate class schedules.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Student roster</li>
        <li>Programme and module registrations</li>
        <li>Enrolment volumes</li>
        <li>Timetabling constraints</li>
      </ul>
      <p><strong>Flow type:</strong> SIS distribution — Timetabling must consume enrolment data from SIS; independently maintained student lists in the timetabling system create divergence risk and inaccurate room and resource allocation.</p>
      <a href="#flows">Back to Flows</a>
  </section>
  <section id="F-TTB-SIS-01" class="blog-article anchor-scroll">
      <h3>F-TTB-SIS-01: Timetabling to Student Records</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Finalised timetable and room allocation data &nbsp;|&nbsp;
        <strong>From:</strong> Timetabling &nbsp;|&nbsp; <strong>To:</strong> Student Records</div>
      <p><strong>Description:</strong> The Timetabling system sends finalised scheduling information and related updates
        back to Student Records so students and administrative staff have consistent data.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Class schedules</li>
        <li>Room allocations</li>
        <li>Time slots</li>
        <li>Instructor availability</li>
      </ul>
      <p><strong>Flow type:</strong> Outcome confirmation — Students access their timetable via the portal (F-SIS-EWP-01); that publication depends on this flow completing successfully first.</p>
      <a href="#flows">Back to Flows</a>
  </section>
  <section id="F-CRM-SIS-01" class="blog-article anchor-scroll">
      <h3>F-CRM-SIS-01: CRM to Student Records</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Applicant, offer, and admissions decision data &nbsp;|&nbsp;
        <strong>From:</strong> CRM &nbsp;|&nbsp; <strong>To:</strong> Student Records</div>
      <p><strong>Description:</strong> The CRM system manages prospective student enquiries, applications, and
        admissions decisions before individuals become enrolled students. This data flows to Student Records so that the
        institution can officially register admitted individuals.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Prospect data</li>
        <li>Applications</li>
        <li>Offers</li>
        <li>Admissions decisions</li>
      </ul>
      <p><strong>Flow type:</strong> SOR intake — This is the handover point from the admissions process to the student lifecycle record; CRM owns the prospect, SIS owns the enrolled student.</p>
      <a href="#flows">Back to Flows</a>
  </section>
  <section id="F-SIS-CRM-01" class="blog-article anchor-scroll">
      <h3>F-SIS-CRM-01: Student Records to CRM</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Student enrolment status and progression updates &nbsp;|&nbsp;
        <strong>From:</strong> Student Records &nbsp;|&nbsp; <strong>To:</strong> CRM</div>
      <p><strong>Description:</strong> Once a prospect becomes an enrolled student, Student Records manages their
        academic progress. Relevant updates flow back to the CRM so the institution can maintain accurate engagement
        information and communications.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Student record status</li>
        <li>Enrolment history</li>
        <li>Progression outcomes</li>
        <li>Qualification records</li>
      </ul>
      <p><strong>Flow type:</strong> SIS distribution — CRM should not independently maintain academic status; updates here ensure engagement, retention, and alumni workflows operate from the authoritative record.</p>
      <a href="#flows">Back to Flows</a>
  </section>

      <div class='flow-meta'><strong>Flow name:</strong> Library loans, fines, and overdue notifications &nbsp;|&nbsp;
        <strong>From:</strong> Library &nbsp;|&nbsp; <strong>To:</strong> Student Records</div>
      <p><strong>Description:</strong> The Library system sends circulation updates and overdue notifications to Student
        Records so that the student record accurately reflects any outstanding obligations or statuses.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Loans</li>
        <li>Overdues</li>
        <li>Fines</li>
        <li>Holds</li>
        <li>Return status</li>
      </ul>
      <p><strong>Flow type:</strong> Outcome confirmation — Outstanding fines or unreturned items may trigger an academic hold in SIS, which can block progression or graduation until resolved.</p>
      <a href="#flows">Back to Flows</a>
  </section>

      <h3>F-SIS-LIB-01: Student Records to Library</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Student enrolment status and access rights &nbsp;|&nbsp;
        <strong>From:</strong> Student Records &nbsp;|&nbsp; <strong>To:</strong> Library</div>
      <p><strong>Description:</strong> Student Records provides the Library with up-to-date student status and
        registration data so library privileges can be granted or restricted appropriately.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Student IDs</li>
        <li>Registration status</li>
        <li>Programme affiliation</li>
        <li>Access rights</li>
        <li>Holds</li>
      </ul>
      <p><strong>Flow type:</strong> SIS distribution — Library access eligibility is derived entirely from SIS enrolment status; withdrawal or suspension events in SIS should drive immediate access restriction.</p>
      <a href="#flows">Back to Flows</a>

        <strong>From:</strong> Student Records &nbsp;|&nbsp; <strong>To:</strong> Finance</div>
      <p><strong>Description:</strong> Student Records provides Finance with key enrolment and fee-related data so the

      <p><strong>Typical data exchanged:</strong></p>

        <li>Tuition charges</li>
        <li>Payment plans</li>
        <li>Scholarships and bursaries</li>

      <h3>F-FIN-SIS-01: Finance to Student Records</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Payment confirmations and financial hold status &nbsp;|&nbsp;
        <strong>From:</strong> Finance &nbsp;|&nbsp; <strong>To:</strong> Student Records</div>
      <p><strong>Description:</strong> Finance is the system of record for financial transactions, invoices, and payment
        processing. Once a financial event occurs, Finance transmits the outcome to Student Records, which becomes the
        system of record for the effect on the student&#x27;s standing.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Payments</li>
        <li>Refunds</li>
        <li>Outstanding balances</li>
        <li>Financial holds</li>
      </ul>
      <p><strong>Flow type:</strong> Outcome confirmation — Finance owns the transaction process; SIS holds the student-facing hold or clearance. An unresolved financial hold can block enrolment confirmation, module registration, or graduation.</p>
      <a href="#flows">Back to Flows</a>
  </section>

        <li>Grades</li>
        <li>Notifications</li>

      <h3>F-VLE-SIS-01: Virtual Learning Env to Student Records</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Assessment grades, completion status, and academic alerts
        &nbsp;|&nbsp; <strong>From:</strong> Virtual Learning Env &nbsp;|&nbsp; <strong>To:</strong> Student Records

        data required to carry out their standards assurance role prior to and during the Exam Board.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Sample scripts access</li>
        <li>Candidate profiles</li>
        <li>Pre-board calculations</li>
        <li>Borderline case indicators</li>
      </ul>
      <p><strong>Flow type:</strong> Governance prerequisite — The External Examiner must receive data with sufficient lead time for meaningful scrutiny; this flow must complete before the board meets to satisfy external examining obligations.</p>
      <a href="#flows">Back to Flows</a>
  </section>
  <section id="F-EXTEX-EXAMBOARD-01" class="blog-article anchor-scroll">
      <h3>F-EXTEX-EXAMBOARD-01: External Examiner to Exam Board</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Standards assurance confirmation and ratification input
        &nbsp;|&nbsp; <strong>From:</strong> External Examiner &nbsp;|&nbsp; <strong>To:</strong> Exam Board</div>
      <p><strong>Description:</strong> The External Examiner provides the Exam Board with independent standards
        assurance commentary, including scrutiny of marking standards, commentary on borderline or contentious cases,
        and confirmation that outcomes are fair and comparable with sector expectations.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Standards assurance commentary</li>
        <li>Sign-off status</li>
        <li>Ratification input</li>
      </ul>
      <p><strong>Flow type:</strong> Governance prerequisite — External Examiner confirmation is a prerequisite for formal ratification; this flow must complete before the Exam Board can return ratified outcomes to Student Records via F-EXAMBOARD-SIS-01.</p>
      <a href="#flows">Back to Flows</a>
  </section>
  <section id="F-AI-SIS-01" class="blog-article anchor-scroll">
      <h3>F-AI-SIS-01: Academic Integrity to Student Records</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Academic misconduct outcomes and penalties &nbsp;|&nbsp;
        <strong>From:</strong> Academic Integrity &nbsp;|&nbsp; <strong>To:</strong> Student Records</div>
      <p><strong>Description:</strong> The Academic Integrity system is the system of record for academic misconduct
        investigations and decisions. Once a case is concluded, the confirmed outcome and any associated penalty are
        transmitted to Student Records.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Misconduct outcomes</li>
        <li>Penalties</li>
        <li>Case closure references</li>
      </ul>
      <p><strong>Flow type:</strong> Outcome confirmation — Misconduct outcomes must be recorded in SIS before board papers are prepared (F-SIS-EXAMBOARD-01); a penalty not yet in SIS cannot be surfaced to the Exam Board for classification consideration.</p>
      <a href="#flows">Back to Flows</a>
  </section>
  <section id="F-SIS-AI-01" class="blog-article anchor-scroll">
      <h3>F-SIS-AI-01: Student Records to Academic Integrity</h3>
      <div class='flow-meta'><strong>Flow name:</strong> Student identity, module registrations, and submission context for misconduct case management &nbsp;|&nbsp; <strong>From:</strong> Student Records &nbsp;|&nbsp; <strong>To:</strong> Academic Integrity</div>
      <p><strong>Description:</strong> Student Records provides the Academic Integrity system with the student identity data, module and assessment registrations, and submission records required to initiate and manage misconduct cases. Academic Integrity is the system of record for the investigation and decision process; Student Records is the system of record for the outcome.</p>
      <p><strong>Typical data exchanged:</strong></p>
      <ul class='data-list'>
        <li>Student identity</li>
        <li>Module and assessment registrations</li>
        <li>Submission records and timestamps</li>
        <li>Enrolment status</li>
      </ul>
      <p><strong>Flow type:</strong> SIS distribution — Case management in Academic Integrity must be grounded in the authoritative SIS record of enrolment and submission; independently maintained student data in AI creates inconsistency and audit trail risk.</p>
