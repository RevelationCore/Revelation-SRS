# Phase 11 Implementation Plan — Hardening and Open Source Release

> Date: 2026-06-18
> Status: Draft (v2 — revised after review; addresses all identified issues and gaps)
> Prerequisite: Phase 10.5 complete
> Roadmap: `docs/project-roadmap.md` Phase 11

---

## Overview

Phase 11 brings Revelation SRS from feature-complete demo readiness to a release state suitable for institutional adoption and open-source publication.

The phase consumes the Phase 10.5 demo-data platform as its hardening baseline. S0 `ci-golden` is used for fast full-stack checks; S6 `institution-year` is used for the 50,000-student design point, performance profiling, security isolation checks, accessibility audit content density, backup/restore rehearsal, and operational runbook validation.

Phase 11 is not a feature-expansion phase. New product functionality is permitted only where it closes Phase 10, Phase 10.5, NFR, security, accessibility, deployment, migration, or release-readiness gaps.

---

## Target Outcomes

By the end of Phase 11:

- performance targets are met and documented against S6 at the 50,000-student design point, including peak-load scenarios (start-of-year enrolment, results publication, UCAS Clearing) and horizontal-scaling proof;
- SAST (CodeQL), dependency scanning, container scanning (Trivy), Compose-based DAST, and tenant-isolation penetration checks are clean or have accepted low-risk exceptions; a final production-shaped DAST pass completes in Stage 10;
- WCAG 2.1 AA automated and manual audits (including screen reader testing with NVDA and VoiceOver) are complete for `apps/admin` and `apps/portal`;
- OpenTelemetry distributed tracing propagates end-to-end through API, modules, adapters, and NATS consumers (NFR-OBS-003);
- domain logic test coverage meets the 90% line-coverage threshold (NFR-TEST-003);
- data-at-rest and backup encryption are documented and verified in the production deployment model (NFR-SEC-002);
- Keycloak account lockout policy satisfies NFR-SEC-005;
- HESA Student Record returns are validated against the current HESA coding manual rules (NFR-REG-001);
- automated retention and anonymisation enforcement is implemented (NFR-PRIV-003);
- the notification centre delivers real-time portal notifications via Server-Sent Events (SSE) backed by a NATS JetStream consumer;
- Phase 10 and Phase 10.5 residual registers are closed or explicitly deferred beyond the initial release;
- production Kustomize deployment assets, secrets integration (OpenBao), backup/restore, and network policy configuration are tested;
- data migration tooling and synthetic SITS-style and Banner-style import mappings are published with validation reports;
- operational runbooks cover startup, shutdown, incidents, recovery, upgrades, demo rotation, and release promotion;
- open-source release artefacts are complete: licence hygiene, SBOM (syft/SPDX), container image signing (Sigstore/cosign), DCO governance, contribution docs, security policy, issue/PR templates, developer setup, architecture index, and v1.0.0 release notes.

## Key Decisions Established at Stage 0

The following decisions are made in Stage 0 and must not be re-opened in later stages:

| Decision | Resolution |
|---|---|
| Notification transport (portal push) | Server-Sent Events (SSE) over HTTP/2 — unidirectional, browser-native, no extra infrastructure. Fastify SSE via `text/event-stream`. NATS JetStream consumer fans out to active SSE connections. |
| Release versioning scheme | Semantic versioning (semver). Release candidate: `v1.0.0-rc.1`. Final release: `v1.0.0`. |
| Deployment templating | Kustomize overlays (base + environment overlays). Consistent with architecture doc `infra/k8s/base/` structure. Helm is not used. |
| Contributor governance | Developer Certificate of Origin (DCO) — no CLA required. Standard for AGPL projects. `DCO` file added to repository; `CONTRIBUTING.md` includes sign-off instructions. |
| Source file header policy | No per-file copyright headers required. AGPL licence notice in root `LICENSE`. Package-level `SPDX-License-Identifier: AGPL-3.0-or-later` in `package.json` metadata. |
| SAST tool | CodeQL (GitHub Actions `github/codeql-action`) — free for open-source repositories, covers TypeScript and security queries. |
| DAST scope split | Stage 3: Compose-based DAST (structural security sweep, pre-production). Stage 10: K8s-based DAST (final production-shaped pass). Both required before v1.0.0. |
| SBOM format | SPDX 2.3 generated by syft. Attached to each release as `sbom.spdx.json`. |
| Frontend Dockerfiles | Created in Stage 1 (`infra/docker/portal/Dockerfile`, `infra/docker/admin/Dockerfile`) — required by Stage 7 K8s manifests. |
| Exception acceptance process | An exception to a release gate requires: written description, severity assessment, mitigation rationale, approval recorded in `docs/release/phase-11/release-checklist.md`. Any CRITICAL or HIGH unmitigated security finding cannot be accepted as an exception. |

## Stage 2 — Performance and Scalability Hardening

**Status**: Pending

**Goal**: prove and tune the system against the 50,000-student design point and peak-load periods.

### Scope

- Use S6 `institution-year` as the performance baseline dataset.

**k6 load suites** — add scenarios for:
- Student portal dashboard, profile, modules, results.
- Staff student search and detail.
- Module selection peak.
- Mark submission and result lookup.
- Exam board data-pack access.
- HESA/regulatory report generation trigger paths.
- Integration health and exchange lists.

**Peak-load profiles** (NFR-PERF-006):
- Add a `start-of-year-enrolment` k6 scenario simulating the burst pattern: 5× normal concurrent sessions, 80% of sessions targeting enrolment and module selection endpoints, ramped over 10 minutes.
- Add a `ucas-clearing-spike` k6 scenario: sudden 10× burst over 2 minutes, targeting admissions and identity endpoints, sustained for 5 minutes.
- Both scenarios must meet NFR-PERF-001 (p95 ≤ 500ms for interactive endpoints) with no error rate above 0.1%.

**Horizontal scaling verification** (NFR-PERF-004):
- Deploy two API instances behind a load balancer (nginx or Docker Compose scale) against S6 in CI.
- Verify that throughput under S6 normal load increases proportionally when a second instance is added.
- Verify no shared in-process state that would cause cross-instance session or cache inconsistency.
- Document the horizontal scaling model in `docs/release/phase-11/performance-report.md`.

**Measure and verify**:
- Interactive API p95 against NFR-PERF-001 (≤ 500ms) and NFR-PERF-007 (single-record DB ≤ 50ms).
- Batch operations (HESA return generation, exam board data-pack generation, BI extracts, S6 demo validation) against NFR-PERF-003: verify they do not degrade interactive API p95 while running.
- Publish S6 load-time metric as a CI artefact and trend chart; close Phase 10.5 residual RR-005.

**Fix bottlenecks found**:
- Missing database indexes.
- N+1 route patterns.
- Slow reports.
- Over-fetching in UI pages.

**Aggregate reporting endpoint** (Phase 10 residuals R-API-001 and R-PERF-002):
- Add `GET /api/v1/reporting/enrolment-volumes` aggregate endpoint.
- Returns total/active/by-status/by-programme counts server-side.
- Removes the client-side N+1 pattern in `EnrolmentReportPage`.

**Scheduled k6 runs**:
- Add a weekly scheduled CI workflow running the full k6 suite against S6 in a staging environment.
- Publish load-time trend artefact.

### Deliverables

- k6 performance suite with all scenarios including peak-load profiles.
- Scheduled performance workflow.
- S6 load-time trend artefact (closes RR-005).
- `docs/release/phase-11/performance-report.md` covering all NFR-PERF IDs including NFR-PERF-004 (horizontal scaling) and NFR-PERF-006 (peak loads).
- Query/index tuning changes.
- `GET /api/v1/reporting/enrolment-volumes` aggregate endpoint.

### Exit Criteria

- Interactive API p95 ≤ 500ms under S6 normal load (NFR-PERF-001).
- Single-record DB lookup p95 ≤ 50ms for benchmarked paths (NFR-PERF-007).
- Batch operations do not breach interactive API targets under concurrent load (NFR-PERF-003).
- Peak-load scenarios (enrolment burst, Clearing spike) meet p95 ≤ 500ms with error rate ≤ 0.1% (NFR-PERF-006).
- Horizontal scaling proof documented: two-instance throughput is within 10% of 2× single-instance throughput (NFR-PERF-004).
- S6 load-time budget is tracked and under the 30-minute ceiling before release candidates.

## Stage 6 — Data Migration Tooling and Validation Framework

**Status**: Pending

**Goal**: publish a credible migration path for institutions moving from common UK SRS platforms.

### Scope

**Migration tooling package**:
- Create `packages/migration-tools/` within the monorepo.
- Define canonical import contracts (TypeScript interfaces + JSON schema) for:
  - student identity (name, identifiers, contact, addresses);
  - enrolments (programme, status, mode, year of entry, dates);
  - programme/module catalogue;
  - module registrations and results;
  - awards;
  - adjustments and EC outcomes where lawfully transferable;
  - audit/history where available from the source system.

**Example SITS-style and Banner-style mappings**:
- Publish synthetic example mapping templates for SITS-style and Banner-style exports.
- **Important IP constraint**: published mappings must be based exclusively on publicly available vendor documentation (SITS data dictionaries, Banner integration API documentation). No proprietary schema structures may be reproduced. Templates are synthetic and representative — they demonstrate the mapping pattern, not a certified production connector. This must be stated clearly in the migration runbook.
- Each template maps source field names to the canonical import contract.

**Validation report implementation**:
- Record counts (source vs loaded).
- Referential integrity checks (all FK targets resolvable).
- Value-set mapping failures (unmapped domain codes).
- **Bitemporal reconstruction checks**: verify imported records form a valid bitemporal history — no overlapping `valid_from`/`valid_to` windows within a logical ID, `valid_from` < `valid_to` where `valid_to` is non-null, `recorded_at` monotonically increasing per logical ID.
- Unresolved external references (identifiers that don't map to known persons, programmes, etc.).
- Privacy/special-category warnings (flagging fields that contain health, disability, or financial data that triggers enhanced handling obligations).

**Dry-run and staged import**:
- All import commands support `--dry-run` (validate without writing).
- Import is phase-aware: `identity` → `enrolments` → `registrations` → `assessment` (mirrors demo-data `LoadPhase` pattern).
- Rollback guidance: import within a transaction; rollback if validation fails.

**Migration runbook**:
- Document limitations (not a certified vendor connector, no real-time sync, no guaranteed schema coverage).
- Document institutional responsibilities (data quality, lawful basis, backup before import).
- Document the dry-run → validation report → staged import → verification workflow.

**Sample fixtures**:
- Synthetic SITS-style and Banner-style import fixtures using fictional data only.
- `test/migration-sits.int.test.ts` and `test/migration-banner.int.test.ts` — validate and load synthetic fixtures into a clean Testcontainers tenant.

### Deliverables

- Synthetic SITS-style and Banner-style mapping templates (with IP constraint notice).
