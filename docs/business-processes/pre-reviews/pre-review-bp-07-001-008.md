## Summary

The product has a sound regulator-neutral spine: a collection with snapshot, records, lineage, validation, sign-off and submission, plus workflow-gated submission approval for HESA, OfS, SLC, UCAS and UKVI. It does not yet produce a lawful statutory return for any nation.

- **HESA:** the return is a 12-field, pre-Data Futures flat file, and its population is entrants only.
- **OfS:** the "B3 extract" is not a return the OfS takes.
- **Student finance:** has no scheme dimension (SFE, SFW, SFNI, SAAS), and sends the wrong effective date for changes of circumstance.
- **SFC, Medr and DfE NI:** exist only as regulator codes.

ADR-018 is only partly applied. Submission does not require a sign-off, the sign-off is not tied to a snapshot, and receipts and payload hashes are missing from the generic model.

Findings: **1 Blocker, 9 Major, 3 Minor, 1 Observation.** The Blocker blocks production use, not Alpha.

## Findings

| # | Severity | Finding | Evidence | Change |
|---|---|---|---|---|
| R07-1 | Blocker (pre-production) | **The HESA "return" is not Data Futures.** It serialises a flat `<StudentReturn><Student>` with legacy C-series field names (HUSID, MSTUFEE, YEARPRG, SBJCA and others). Data Futures is an entity model (Student, Engagement, StudentCourseSession, Course, Module and so on), and it is validated on the HESA Data Platform. Several fields are also wrong: `YEARPRG` is hard-coded to 1, `SBJCA` is the owning school (not a HECoS subject), and MODE maps `distance`→03 and `sandwich`→04, which are not valid codes for those modes. | `hesa-service.ts` `mapStudentToHesa`, `serialiseHesaXml`, `mapMode` | Label it in the UI as a placeholder, not a submission. Build the Data Futures entity mapping from the current coding manual (versioned per year, ADR-018). Until then, the export should be an extract for a provider's own Data Futures tool. |
| R07-2 | Major | **The HESA population is entrants only.** The source query filters `academic_year_of_entry = academicYear`, so continuing, returning and leaving students are left out. The Data Futures population is engagements active in the reference period. | `hesa-service.ts` `#loadSourceRows` | Define the population by engagement activity in the reference period, with coverage rules per the manual. |
| R07-3 | Major | **There is no frozen source cut-off.** Extraction reads current rows (`recorded_until IS NULL`) at run time, not as of the snapshot's `source_transaction_time`. `regulatory_collection` also has none of ADR-018's specification/schema version, reference period, provider scope (UKPRN) or deadlines. | `hesa-service.ts`; `regulatory.ts` `regulatoryCollections`, `collectionSnapshots` | Use bitemporal as-of reads at the snapshot time, and add the ADR-018 collection attributes. |
| R07-4 | Major | **Sign-off does not control submission.** `submit()` needs no sign-off and does not check that the snapshot belongs to the collection. `regulatory_signoff` has no snapshot ID, so a sign-off covers whatever is later submitted. Sign-off and submit need only `regulatory:write`, which `system-administrator`, `tenant-administrator` and `dpo` also hold, and nothing requires the signer to differ from the preparer. HESA requires sign-off by the head of provider; the OfS and the funders require an accountable signatory. | `regulatory-collection-service.ts` `signOff`, `submit`; `routes/regulatory-collections.ts`; `permissions.ts` line 145 | Bind the sign-off to the snapshot version and its content hash. Require it before submit. Add a `regulatory:sign-off` permission for an accountable-officer role, with signer ≠ preparer. |
| R07-5 | Major | **The submission and quality-query model is incomplete.** `regulatory_submission` has no payload hash, channel, receipt or amendment/supersedes link. `regulatory_validation_issue` has no disposition, owner or BP-07-008 classification (source error, transform error, timing difference, valid exception). `recordFieldLineage` has no route. | `regulatory.ts`; capability limitation text | Add these to the generic model; the HESA-specific tables already have a payload hash and amendment link. |
| R07-6 | Major | **The OfS B3 extract is misconceived.** The OfS calculates B3 student-outcome indicators itself from individualised student data (HESA Data Futures or ILR). Providers do not submit a B3 extract; their OfS returns are set by the F3/F4 Notice. The extract is also deliberately re-derived live at approval time, contrary to ADR-018. | `ofs-service.ts` lines 29, 112, 242; SRC-066 | Reposition it as internal monitoring that reconciles to the OfS dashboards, and freeze its inputs. Catalogue the real OfS returns from the 2026-27 Notice with the OfS reviewer. |
| R07-7 | Major | **Student finance has no scheme or channel dimension.** Nothing records whether a student is funded by SFE, SFW, SFNI or SAAS. SAAS uses its own channel, not SLC's. The inbound value set covers only entitlement, payment, overpayment and recovery. A status-change notification carries start and expected-end dates but not the event's effective date (the last date of attendance), which drives liability and overpayment. Its idempotency key `slc-status:{enrolment}:{status}` collides on a second, legitimate event of the same type, such as a second suspension. The fee lookup takes `.limit(1)` with no year. | `slc-service.ts` `generateStatusChangeNotification`, `generateConfirmations`; seed `slc-notification-type-code` | Add the funding body or scheme per enrolment and year, a per-scheme contract, an event effective date taken from the status case, an idempotency key that includes the status-transition ID, and a fee lookup by year. |
| R07-8 | Major | **There is no Lifelong Learning Entitlement readiness.** Applications opened in September 2026 for courses starting from 2027-01-01. Providers must give SLC course and module data with credit values for January 2027 starters. The SLC exchange is enrolment-level only. | LLE provider guidance (2026-07-31); `slc-service.ts` | Decide the LLE scope for England (modular attendance and credit confirmation) with the student-finance reviewer. |
| R07-9 | Major | **SFC, Medr and DfE NI are codes only.** No return catalogue, specification, coding boundary or sign-off rule exists for any of them. The pages describe the returns generically. Medr's registration regime began on 2026-08-01, with full requirements from August 2027, and Medr/2026/35 moves TNE and award-only provision off the HESA student record from 2026/27. | `regulatory.ts` `regulatorCode`; capability limitation; Medr sources | Have each national reviewer list the returns, channels and signatories in scope, and record them as configuration per regulator. |
| R07-10 | Major | **There is no UKVI reporting-deadline control.** `ukvi_sponsor_decision` keeps decision and authorisation apart (decider ≠ authoriser is enforced), but it has no event date, reporting deadline or overdue alert for the 10-working-day sponsor reporting duties. | `ukvi-service.ts` line 451; `regulatory.ts` `ukviSponsorDecisions` | Add a reportable-event date and a computed deadline (the working-day calendar exists in `non_working_day`), with an escalation. |
| R07-11 | Minor | **Local HESA validation is thin and uses the wrong date.** There are five hand-written checks, and the age check uses the clock, not the reference date. They must not be presented as HESA quality rules. | `hesa-service.ts` `validateHesaRecords` | Rename them "pre-checks" and use the reference-period date. Quality rules come from the HESA Data Platform. |
| R07-12 | Minor | **In-year collection is not modelled.** The 2025/26 in-year return was paused, and the OfS is phasing in in-year collection. The model is keyed by academic year only. | HESA and OfS sources above | Add a reference period below the academic year so that several submissions per year fit without schema change. |
| R07-13 | Minor | **There is no retention rule for return artefacts.** `hesa_student_return_record.record_payload` and `regulatory_record.record_payload` keep names, dates of birth and special-category fields for every version. The data-subject coverage matrix lists "statutory return artefacts" as an outstanding register update. | [Data-subject coverage matrix](../../architecture/data-subject-coverage-matrix.md), item 4 | Add a retention class (proposed: until the collection closes plus the regulator's amendment window, then hash and summary only) for the records manager to confirm. |
| R07-14 | Observation | **The process pages are stale.** Their BR-3 rows say that what now exists does not. For example, BP-07-002 says there is no exchange ledger, though `integration_exchange` exists, and BP-07-004 says there is no OfS workflow, though `ofs_extract` exists and is workflow-gated. The four national-variation paragraphs are identical on every page. | Pages BR-3 | Refresh BR-3 and the variations when the pages are next revised (the owner is the documentation lead). |
